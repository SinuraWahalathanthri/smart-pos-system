How to read this document

Categories A–J are normalized base tables governed by BCNF. Category K is deliberately outside BCNF: those tables hold pre-computed aggregates for dashboards and are rebuilt from the base tables, never written by hand. Section Views lists the derived relations that replace the stored stock_on_hand / packets_on_hand columns in the current PostgreSQL schema.

All identifiers are BINARY(16) UUIDs unless the table is a high-volume ledger (BIGINT UNSIGNED AUTO_INCREMENT plus a unique client UUID for idempotency). All timestamps are DATETIME(3) stored in UTC; see the 2038 note below. All money columns are integer minor units (cents) named *_cents.

PostgreSQL to MariaDB: what actually changes

The current backend leans on four Postgres/Supabase features that MariaDB does not have. These are not cosmetic differences; two of them change the architecture.

Postgres / SupabaseMariaDB replacementConsequence
Row Level Security (22 policies) Nothing equivalent Architectural. Tenant isolation must move out of the database.
SECURITY DEFINER functions as the write gateway CREATE PROCEDURE + SQL SECURITY DEFINER, or an application service Writes still validated centrally, but callable by anyone holding the DB login unless GRANT is tight.
jsonb + GIN indexes JSON (validated LONGTEXT) No containment queries or GIN. Promote queryable fields to real columns; JSON only for opaque payloads.
uuid BINARY(16) + UUID_TO_BIN(x, 1) 16 bytes vs 36. The 1 (swap) flag reorders the timestamp for clustered insert locality; requires MariaDB 10.7+.
timestamptz DATETIME(3) in UTC TIMESTAMP in MariaDB is 32-bit and dies in 2038. Use DATETIME for anything long-lived.
crypt() (pgcrypto bcrypt) Application-side bcrypt / argon2id Hashes live in staff_credentials. The DB never sees a plaintext PIN.
Triggers using set_config() to bypass guards Stored procedure owning the write; no guard bypass variable The app.stock_write trick has no equivalent; the ledger write becomes a procedure call.
Partial indexes Generated column + normal index e.g. is_open generated flag on shifts for an efficient open-shift lookup.
ON CONFLICT DO NOTHING INSERT … ON DUPLICATE KEY UPDATE Idempotent sale re-submission still works, keyed on the client UUID.
numeric(12,3) DECIMAL(12,3) Identical semantics. Weights and quantities keep 3 decimals.
The one decision you must make before this is built

Today the database is the security boundary: 22 RLS policies mean a stolen anon key cannot read another store's sales, and cashiers physically cannot write a sale except through complete_sale(). MariaDB has no RLS. Once the schema moves, that guarantee disappears from the database layer and must be re-created somewhere else:

Option 1 (recommended) — a thin TypeScript service tier owns all writes, holds the DB credentials, resolves the tenant from the session, and calls stored procedures. The browser never touches MariaDB. This preserves the current security posture and is a smaller change than it sounds, because the RPC surface is already the only write path.

Option 2 — one MariaDB account per role plus SQL SECURITY DEFINER views and procedures, with column-level GRANTs hiding cost_cents and credential hashes. Weaker: any credential leak is a full-tenant leak, and there is no per-row isolation.

Option 3 (not recommended) — connect the browser directly. There is then nothing between an attacker and every store's data.

What MariaDB gives back

CHECK constraints are enforced (10.2+), which Postgres 15 also has but the current schema barely uses. GENERATED … STORED columns make derived money values real columns that cannot drift, which is how this schema removes several BCNF violations rather than merely documenting them. Native InnoDB partitioning, mature replication, and predictable single-binary operations are genuine wins for a shop that may run its own server.

Normalization to BCNF

A relation is in BCNF if, for every non-trivial functional dependency X → Y, X is a superkey. The current 17-table schema violates this in nine places. Each violation, and the decomposition that removes it, is listed below.

#Relation / attributeViolating dependencyWhy it fails BCNFFix in this schema
1 pack_sizes.label label → weight_g "250 g" always means 250 grams, so label determines weight_g but is not a superkey. Two rows could disagree. weight_labels(weight_g PK, label); pack_sizes drops label.
2 products.stock_on_hand
pack_sizes.packets_on_hand		 Aggregate of stock_movements A stored sum is not functionally determined by the row's key; it is determined by other rows. Update anomaly by construction. Columns removed. v_stock_levels computes SUM(qty_change).
3 sale_items.line_total_cents
tax_cents		 qty, unit_price → line_total
line_total, rate → tax		 The determinant is not a superkey, so the value can contradict its inputs. GENERATED … STORED columns: computed by the engine, impossible to disagree.
4 sales.total_cents subtotal, discount → total Same shape as #3: derived within the row. GENERATED … STORED on the row.
5 bottle_ledger.amount_cents qty, store.bottle_fee → amount The fee lives in another table, so the amount silently becomes wrong when the fee changes. Classic update anomaly. Snapshot fee_unit_cents onto the row; amount_cents generated from qty × fee_unit.
6 products.tax_rate_pct tax_class → rate, copied onto every product The rate is a fact about the class, not the product. A VAT change must touch every row, and a missed row is a wrong tax return. tax_classes(tax_class_id PK, rate_bp, is_inclusive); products reference it. Sales still snapshot the rate.
7 product_barcodes.store_id
pack_sizes.store_id
product_costs.store_id		 product_id → store_id store_id is transitively determined by the parent, so it is redundant in the child and can contradict it. Dropped from these children; derived by join or via a view.
8 profiles (person + credential + role + device) auth_user_id → store_id, role with auth_user_id UNIQUE Technically BCNF, but four independent entities are fused into one relation, which is why a person can belong to exactly one store. Decomposed into staff, staff_credentials, store_memberships, devices.
9 notifications.title, body product_id → products.name, copied into the message Renaming a product leaves stale alert text behind, and the copy cannot be reconciled. Store type_code, product_id and params JSON; render the text in the app.
10 settings (EAV key/value) No declared dependency; typed by convention only Not a normal-form violation but an untyped relation: any key, any value, no constraint. Typed 1:1 store_settings with a CHECK per column.

Deliberate denormalization register

Some redundancy is required by law or by physics. Rather than pretend otherwise, every such field is registered here with its justification and the mechanism that keeps it correct. Nothing else in the schema is allowed to be redundant.

FieldDuplicatesWhy it must stayHow it is kept correct
sale_items.name_snapshot
label_snapshot
tax_rate_bp		 products.name, weight_labels.label, tax_classes.rate_bp An issued invoice is a legal document. If a product is renamed or VAT changes tomorrow, last month's receipt must not change. Written once at sale time; the table is insert-only for these columns (no UPDATE grant).
sales.subtotal_cents
tax_included_cents		 Aggregate of sale_items The posted total is the figure the customer paid and the figure that was receipted. Recalculated and asserted inside the sale procedure; mismatch aborts the transaction.
stock_movements.store_id
sales.store_id		 Derivable from product_id These are the partitioned, high-volume tables. Tenant filtering and physical partitioning need the column locally. Composite FK to the product's store, so a cross-store row is rejected by the engine.
product_batches.qty_remaining Sum of batch_allocations FEFO allocation must read remaining quantity per batch on every scan; recomputing per line is too slow at the till. Updated in the same transaction as the allocation, with a CHECK (qty_remaining ≥ 0).
*_rollup tables (K) sales + sale_items Dashboard aggregates over millions of rows. Rebuilt on a schedule; explicitly read-only to the app.
Table count: 17 → 50

The growth is not inflation. It is decomposition of fused relations (1 table became 4 in category A), eight lookup tables that carry their own attributes, and four subsystems the current schema never modelled at all: shifts and cash, customers and credit, purchasing and receiving, and production. A schema that answers more questions has more tables; the alternative is columns that mean different things depending on the row.

Ordering of the work, if this is built

1. Category A, B and the ledger in C first â€” they are the spine. 2. Category D plus the sale procedure, because nothing can be sold without it. 3. Open questions this schema forces you to answer

Tenant isolation. With RLS gone, which of the three options in the MariaDB section do you want? This determines whether the procedures are the security boundary or merely a convention.

Receipt numbering. Per-device gapless series is what a VAT inspector expects, but it means an offline till consumes numbers it may never use if the sale is refused on sync. Accept gaps (per-device AUTO_INCREMENT) or accept that a refused sale burns a number?

Late bottle returns. Still undecided in PLAN.md, and it changes bottle_event_types: is fee_refunded a real event, and within what window?

Offline credit. Can a credit sale be written with no connection? If yes, customer_credit_entries can briefly exceed a credit limit; if no, the till must refuse it.
